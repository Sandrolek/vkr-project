# ЛР 2 — обоснование актуальности ВКР

**Тема ВКР:** «Разработка методики безопасного развёртывания MCP-серверов для интеграции LLM-агентов с корпоративными системами в изолированных контурах»

**Автор:** Поляков Александр Владимирович, K3439

Тема относится к безопасности LLM-агентов. Агент на основе большой языковой модели подключается к корпоративным системам через MCP-серверы (Model Context Protocol) и получает право читать и изменять данные: проводить документы в 1С, отправлять письма из корпоративной почты. Если во входящем письме или документе содержится внедрённая инструкция, агент может выполнить её как задание пользователя. В работе исследуется, как развёртывать такие серверы в изолированном контуре без доступа в интернет, чтобы даже обманутый агент не смог причинить ущерб.

Практическая часть ВКР выполняется на платформе AI-агентов для закрытых корпоративных сред, в разработке которой участвует автор. В платформе уже есть собственные MCP-серверы для 1С и почты, подтверждение опасных действий человеком, сетевые политики для части компонентов и стенды для экспериментов.

### Выводы по обзору

- Работы [2, 3, 5] показывают, что агента с инструментами можно заставить выполнить чужую инструкцию из данных, а надёжной защиты на уровне модели нет. Поэтому в работе используется подход ограничения ущерба: агент считается заведомо скомпрометированным, а защита строится в инфраструктуре вокруг него.
- Обзор [1] и спецификация [6] перечисляют угрозы MCP, но не дают методики развёртывания серверов в инфраструктуре заказчика.
- Руководство [7] и приказ [11] задают проверенные меры для контейнерных сред: сетевое разделение, минимальные права, контроль образов. Их можно перенести на MCP-серверы.
- Российские нормативные документы [10, 11] уже требуют для ИИ-систем отдельный сегмент, минимальные права и защиту агентов от воздействия, но не говорят, как выполнить эти требования для MCP-серверов.
- Нерешённым остаётся вопрос: какие меры развёртывания и в каком сочетании останавливают атаки на агента в закрытом контуре и какой ценой для пользователя. На него и отвечает ВКР.

## 3. Обзор и сравнение аналогов

### Прямые аналоги

- **Cisco MCP Scanner** ([GitHub](https://github.com/cisco-ai-defense/mcp-scanner)) — открытый сканер MCP-серверов: проверяет описания инструментов на скрытые инструкции и другие признаки угроз. Ограничения: проверяет сервер до подключения, но не контролирует вызовы во время работы, а часть проверок опирается на внешние сервисы анализа.
- **mcp-scan / Snyk Agent Scan** ([GitHub](https://github.com/invariantlabs-ai/mcp-scan)) — сканер компонентов агента и MCP-серверов на prompt injection и tool poisoning. Ограничения: те же, что у сканера Cisco; права в целевой системе и сетевой доступ сервера не затрагивает.
- **AI Security Gateway** ([описание](https://mcpservers.org/servers/aisecuritygateway-ai-docs-mcp-gateway)) — MCP-шлюз, через который проходят все вызовы инструментов; фильтрует их и ведёт журнал. Ограничения: не ограничивает права служебной учётной записи в целевой системе и не останавливает критичное действие до решения человека.

### Косвенные аналоги

- **NVIDIA NeMo Guardrails** ([GitHub](https://github.com/NVIDIA/NeMo-Guardrails)) — библиотека защитных фильтров для LLM-приложений: проверяет входы и выходы модели по заданным правилам. Работает локально. Ограничения: ничего не знает про MCP и целевые системы, не проверяет описания инструментов и не управляет инфраструктурой.

### Таблица сравнения

**Почему выбраны эти критерии:** критерии следуют из модели угроз и условий эксплуатации. Первый критерий отражает требование закрытого контура: средство, которому нужны внешние сервисы, у заказчика неприменимо. Второй и третий критерии покрывают две главные атаки на агента: отравленные описания инструментов и инструкции, внедрённые в данные. Критерии с четвёртого по шестой оценивают меры ограничения ущерба, которые работают даже после успешной атаки. Седьмой критерий проверяет, повторяется ли защита на каждой установке без ручной настройки. Восьмой нужен для расследования инцидентов.

| Критерий | Cisco MCP Scanner | mcp-scan | AI Security Gateway | NeMo Guardrails (косвенный) | Наше решение (план) |
|---|:-:|:-:|:-:|:-:|:-:|
| Работа в изолированном контуре без внешних сервисов | ± | ± | ± | + | + |
| Проверка описаний инструментов на tool poisoning | + | + | + | − | + |
| Защита от инструкций, внедрённых в данные | − | ± | ± | ± | ± |
| Подтверждение критичных действий человеком | − | − | − | − | + |
| Минимальные права в целевой системе (1С, почта) | − | − | ± | − | + |
| Сетевая изоляция каждого сервера | − | − | − | − | + |
| Меры встроены в конвейер поставки | ± | ± | − | − | + |
| Аудит вызовов инструментов | − | ± | + | − | + |

Обозначения: «+» — поддерживается, «±» — поддерживается частично, «−» — не поддерживается. Оценки аналогов сделаны по их документации. В столбце «Наше решение (план)» указаны планируемые свойства методики. Подтверждение критичных действий человеком в платформе уже есть, а проверка описаний на tool poisoning, сетевая изоляция всех серверов и аудит — цели ВКР.

### Выводы по сравнению

- Аналоги защищают сам протокол MCP, но не целевую систему: права служебной учётной записи в 1С и сетевой доступ сервера они не затрагивают. Это ограничение ВКР устраняет.
- Ни один аналог не останавливает критичное действие до подтверждения человеком, хотя только эта мера срабатывает даже при успешной prompt injection.
- Полной защиты от инструкций в данных не даёт никто, поэтому ВКР нацелена на ограничение ущерба, а не на полное предотвращение атаки.
- Из существующих решений можно взять сканеры описаний инструментов: их стоит встроить в конвейер поставки как шаг проверки сторонних серверов, если они работают без внешних сервисов. Сканеры также служат базовой линией в эксперименте.

## 4. Итоги

**Итоговая тема ВКР:** «Разработка методики безопасного развёртывания MCP-серверов для интеграции LLM-агентов с корпоративными системами в изолированных контурах». Тема по итогам обзора не изменилась.

**УДК для тезиса:** 004.056 (защита информации), дополнительно 004.8 (искусственный интеллект).

**Ключевые слова:** LLM-агенты, Model Context Protocol, MCP, prompt injection, tool poisoning, модель угроз, DevSecOps, MLOps, изолированный контур, минимальные привилегии, human-in-the-loop.

### Актуальность исследования

Компании подключают LLM-агентов к рабочим системам через MCP, и агент получает право изменять данные и отправлять письма. Исследования [2, 3, 5] показывают, что такого агента можно заставить выполнить чужую инструкцию из письма или документа, а надёжной защиты на уровне модели нет. Одновременно ФСТЭК России готовит требования к защите ИИ-систем, которые вступают в силу 1 марта 2027 года [10]. Существующие средства защищают сам протокол, но не ограничивают ущерб в целевой системе и часто требуют внешних сервисов, недоступных в закрытом контуре (раздел 3).

### Цель исследования

За счёт мер, встроенных в развёртывание MCP-серверов, не дать агенту, которым управляет злоумышленник, выполнить несанкционированную операцию в корпоративной системе или вывести данные за её пределы.

### Задачи исследования

1. Построить модель угроз для связки «агент — MCP-сервер — корпоративная система» по методике STRIDE и перечню OWASP Top 10 for LLM.
2. Сравнить существующие средства защиты MCP и определить, какие угрозы они не закрывают.
3. Разработать набор мер: сетевые политики на каждый сервер, минимальные права служебных учётных записей, управление секретами, подтверждение критичных действий человеком, проверка сторонних серверов, аудит вызовов.
4. Встроить меры в конвейер поставки так, чтобы установка без них не проходила проверку.
5. Прогнать набор атакующих сценариев на стенде без мер и с мерами и измерить долю остановленных атак, число лишних запросов подтверждения и задержку вызовов инструментов.

### Датасеты и сервисы

- **AgentDojo** [3] ([GitHub](https://github.com/ethz-spylab/agentdojo)) — открытый бенчмарк с готовыми сценариями prompt injection для агентов с инструментами, в том числе почтовых. Нужен как воспроизводимая часть атакующего набора. Доступен открыто.
- **Собственный набор атакующих сценариев** под 1С и почту: письма с внедрёнными инструкциями, попытки записи и вывода данных, отравленные описания инструментов. Нужен, потому что в открытых наборах нет сценариев для 1С. Будет собран в ходе работы. Тексты инъекций не публикуются, в отчётах приводятся классы сценариев и статистика.
- **Собственные стенды** — тестовый и предрелизный контуры платформы с тестовыми базами 1С и тестовым почтовым ящиком. Нужны для эксперимента: атаки прогоняются только на тестовых данных. Доступ есть у автора, публично стенды не открываются.
- **Cisco MCP Scanner и mcp-scan** — открытые сканеры, базовая линия для сравнения.
